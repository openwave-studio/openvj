# Contributing

## Specs with OpenSpec

openVJ keeps what it does, and what's being changed, in [`openspec/`](openspec) using [OpenSpec](https://github.com/Fission-AI/OpenSpec):

- `openspec/specs/<capability>/spec.md` describes how openVJ behaves today, one capability per folder (clip grid, decks, Resolume import, MIDI, effects…). It's the shared source of truth for decisions already made.
- `openspec/changes/<change>/` holds work in flight: a `proposal.md` (why, what, which files and specs it touches, what it may conflict with), spec deltas, `tasks.md`, and a `design.md` only when there's a real choice to record.
- `openspec/config.yaml` lists the standing decisions every proposal follows (Resolume compatibility first, ISF effects, one driver per parameter, the openDJ look) and the files where parallel work tends to collide.

### When to use it

Use a change proposal for a **feature**: anything a VJ would notice, a new file format, or a change to a shared model. Skip it for bug fixes, refactors, CI, docs and small UI tweaks; just open a PR.

### Workflow

1. **Propose.** `openspec new change <verb-thing>` (or `/opsx:propose` in Claude Code). Fill in the proposal's *Touches* and *Conflicts* sections by checking `openspec list` for other changes in flight. Open the PR early with just the proposal, so overlaps show up before code is written.
2. **Build.** Implement on the same branch, ticking `tasks.md` as you go (`/opsx:apply`).
3. **Archive.** In the PR that finishes the change, run `openspec archive <change> -y`. It folds the spec deltas into `openspec/specs/` and moves the change to `openspec/changes/archive/`, so main's specs always match main's code.

Run `openspec validate --all --strict` before pushing.

### Installing the CLI

```bash
npm install -g @fission-ai/openspec@1.16.1
# or, without installing: npx -y @fission-ai/openspec@1.16.1 <command>
export OPENSPEC_TELEMETRY=0   # optional: turn off anonymous usage stats
```

The Claude Code skills and `/opsx:*` commands in `.claude/` were generated by `openspec init --tools claude`; regenerate them with `openspec update` after upgrading the CLI.

## Releasing

1. In a PR, set the version in `Cargo.toml` and add its section to `CHANGELOG.md` (`scripts/release-notes.sh <version>` shows the notes it will make).
2. After it merges, publish a release on GitHub with a new tag `v<version>` on `main`. The title and notes can stay empty.
3. The macOS app workflow builds, signs and notarizes the app and attaches the zip; the release notes workflow sets the title to "openVJ v<version>" and the notes from the changelog. To redo the notes later, run Actions → Release notes with the tag.
